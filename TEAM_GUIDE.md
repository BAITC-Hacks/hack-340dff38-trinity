# AI Sana: работа втроём и отправка в GitHub

Это инструкция для уже собранного MVP. Не нужно заново создавать три разных проекта: у команды один репозиторий, у каждого участника своя локальная копия и ветка для конкретной задачи.

Репозиторий Trinity: https://github.com/BAITC-Hacks/hack-340dff38-trinity. Основная ветка — `main`. Когда MVP уже объединён, начинайте с раздела 4; повторный импорт не нужен.

По «Инструкции для участников HackAlem AI», стр. 1–2: итоговый код должен находиться в репозитории команды, выданном платформой; API-ключи нельзя публиковать; после отправки кода нужно выбрать кейс и нажать «Сдать решение». Push сам по себе не завершает сдачу. В документе отведено 5 часов; фактический дедлайн смотрите на платформе.

## 1. Кто за что отвечает

Имена не заданы, поэтому используем номера. Третьего участника назначаем ответственным за общую сборку и сдачу.

| Участник | Зона | Конкретные задачи | Критерий готовности |
|---|---|---|---|
| **1. Frontend / интерфейс** | `frontend/` | Каталог и фильтры, демо-вход, кабинеты, редактор задачи, отправка проекта, просмотр AI-разбора, анонимный чат, выбор победителя, профиль с баллами, экран модерации, мобильная версия | Все три роли проходят свои сценарии; формы показывают ошибки; TypeScript и сборка проходят |
| **2. Backend / база и правила** | `backend/app/core/`, `models.py`, `schemas.py`, `seed.py`, `main.py`, `routers/` кроме `ai.py`, `services/` кроме `ai/`, `backend/migrations/` | API, авторизация и доступ, команды, дедлайны, анонимность, один победитель, начисление баллов один раз, Q&A, чат, модерация, PostgreSQL и миграции | До выбора победителя нет раскрытия авторов; до дедлайна нельзя выбрать победителя; 95/3 даёт по 31.67; повторная оценка не удваивает баланс |
| **3. AI / проверка / интеграция** | `backend/app/services/ai/`, `backend/app/routers/ai.py`, `backend/tests/`, Docker-файлы, `docker-compose.yml`, `start-local.ps1`, README и VALIDATION | AI-интервью, качество задачи, рекомендация срока, разбор решения, AI-модерация, Claude + fallback; проверка тестов и полного сценария; сборка общей версии, инструкция и сдача | Mock работает без ключа; Claude проверен при наличии ключа; AI не выбирает победителя; общая версия запускается по README |

Участник 1 владеет `frontend/src/main.tsx`, `styles.css`, `components/ui.tsx`, `lib/api.tsx`, `lib/types.ts`, `package.json` и `pnpm-lock.yaml`. Участник 3 согласовывает с ним изменения `frontend/Dockerfile` и сборочных скриптов.

Участник 2 владеет общими `schemas.py`, `models.py`, `core/config.py`, `core/enums.py` и `requirements.txt`. Если AI требует новое поле или зависимость, участник 3 сначала согласует это с ним. Python-схемы и TypeScript-типы меняются совместно по одному договорённому JSON-контракту.

Участник 3 координирует общие тесты; участник 2 может добавлять проверки бизнес-правил в отдельный файл тестов. Не редактируйте втроём один большой тестовый файл одновременно. Миграции создаёт участник 2; применённые миграции не переписывают, а добавляют следующие.

### Первые задачи на текущей версии

1. **Участник 1:** запустить frontend, пройти три роли, исправить найденные ошибки интерфейса и проверить мобильную ширину.
2. **Участник 2:** запустить PostgreSQL, применить миграции и seed, проверить конкурентный выбор победителя и начисления. Эти проверки на живом PostgreSQL ещё не выполнялись.
3. **Участник 3:** прогнать тесты, проверить контейнерный запуск; при доступном ключе проверить реальный Claude и `source: "claude"`; обновить VALIDATION только фактическими результатами.

Сейчас подтверждены 24 теста, локальный SQLite/mock и браузерный сценарий. Живой Claude и Docker/PostgreSQL пока не подтверждены; подробности в `VALIDATION.md`.

## 2. Правило веток

- `main` — общая рабочая версия для демонстрации и сдачи.
- `feat/frontend-catalog` — пример задачи участника 1.
- `fix/backend-points` — пример задачи участника 2.
- `feat/ai-claude-check` — пример задачи участника 3.
- На каждую следующую задачу создавайте новую ветку от актуальной `main`. Не держите три постоянные ветки до последнего часа.
- Один человек работает в одной конкретной ветке; остальные смотрят изменения через pull request.
- После начальной загрузки изменения попадают в `main` через pull request, после проверки другим участником.

Здесь `main` — предполагаемая основная ветка. Если репозиторий платформы использует `master` или другое имя, замените `main` во всех командах на фактическое имя. Не переименовывайте ветку, которую ожидает платформа.

`commit` сохраняет изменения локально. `push` отправляет коммиты в GitHub. Pull request (PR) предлагает объединить ветку с `main`. Пока PR не объединён, код есть на GitHub, но его ещё нет в общей версии.

## 3. Подготовка: делает один человек

### 3.1. Получить репозиторий команды

1. Откройте репозиторий, выданный платформой HackAlem AI, и скопируйте его HTTPS URL через `Code`.
2. Убедитесь, что все трое имеют доступ на запись и приняли приглашения. Если доступа нет, решите это через владельца репозитория или платформу.
3. Не создавайте отдельный личный репозиторий вместо выданного платформой.

Команды выполняются в терминале PowerShell или VS Code; каждую строку выполняйте отдельно и не продолжайте после ошибки.

```powershell
git clone https://github.com/BAITC-Hacks/hack-340dff38-trinity.git ai-sana-team
cd ai-sana-team
git remote -v
git status
```

`git remote -v` должен показать именно репозиторий команды. В дальнейшем открывайте в редакторе эту папку, а не старую папку с распакованным ZIP.

В текущей поставке `.git` и GitHub remote отсутствуют. Клонирование создаёт правильную связь с репозиторием; не выполняйте отдельный `git init` внутри клона.

### 3.2. Настроить автора коммитов

Каждый участник делает это в своей копии, указывая собственные данные:

```powershell
git config user.name "Ваше имя"
git config user.email "Ваш email из GitHub"
```

Для приватности можно использовать личный GitHub noreply email. Все не должны коммитить от имени одного человека. Авторизация при push выполняется вашим GitHub-аккаунтом; эти два параметра только подписывают коммиты.

### 3.3. Если в репозитории уже есть коммиты

После клонирования основная ветка уже выбрана. Создайте ветку импорта:

```powershell
git switch -c chore/import-mvp
```

Скопируйте **содержимое** папки `ai-sana` из поставки в корень клона: рядом должны лежать `backend`, `frontend`, `README.md` и `docker-compose.yml`. Не загружайте один ZIP вместо исходников и не создавайте вложенность `ai-sana-team/ai-sana/backend`.

Сохраните имеющиеся файлы платформы, `.github`, лицензию и условия кейса. Если README или другие файлы уже существуют, объедините нужный текст, прежде чем заменять их. Не копируйте `.git`, `.env`, локальные базы, `.venv`, `node_modules` и кэши. Папка `dist` в архиве есть, но Git её игнорирует: для сдачи нужны исходники и команды сборки.

```powershell
git status --short
git add backend frontend scripts .github .gitattributes .editorconfig .gitignore .env.example docker-compose.yml start-local.ps1 README.md VALIDATION.md TEAM_GUIDE.md
git diff --cached --stat
git diff --cached
git commit -m "feat: add AI Sana MVP"
git push -u origin chore/import-mvp
```

Просмотрите staged diff до commit. Затем откройте PR из `chore/import-mvp` в основную ветку, проверьте и объедините его. Остальные начинают работу после этого объединения.

### 3.4. Если репозиторий полностью пустой

Git при clone сообщит, что репозиторий пустой. После копирования файлов и настройки автора сначала создайте начальный коммит:

```powershell
git add backend frontend scripts .github .gitattributes .editorconfig .gitignore .env.example docker-compose.yml start-local.ps1 README.md VALIDATION.md TEAM_GUIDE.md
git diff --cached --stat
git diff --cached
git commit -m "feat: add AI Sana MVP"
git branch -M main
git push -u origin main
```

Это единственный первоначальный push в `main`. Если платформа предписывает другое имя ветки, используйте его. Если GitHub запрещает начальный push правилами репозитория, попросите владельца или поддержку платформы выполнить инициализацию; не обходите правила через force push.

## 4. Как каждому начать свою задачу

После того как начальный MVP появился в основной ветке, два остальных участника клонируют тот же репозиторий; первый продолжает в уже созданном клоне.

```powershell
git clone https://github.com/BAITC-Hacks/hack-340dff38-trinity.git ai-sana-team
cd ai-sana-team
```

Не клонируйте поверх существующей папки с работой. Перед каждой новой задачей, из корня своей копии:

```powershell
git status
git switch main
git pull --ff-only origin main
git switch -c feat/frontend-catalog
```

Перед переключением `git status` должен показывать чистую рабочую папку. Если есть незавершённые изменения, сначала сохраните их коммитом в своей текущей ветке; не удаляйте их ради переключения.

В последней команде участник 1 использует `feat/frontend-catalog`, участник 2 — `fix/backend-points`, участник 3 — `feat/ai-claude-check`. Это примеры имён первых задач, а не команды для создания всех трёх веток одним человеком.

## 5. Как пушить свои изменения

Сначала сохраните файлы в редакторе и выполните проверку своей части. Пример для участника 1:

```powershell
git branch --show-current
git status --short
git diff
git add frontend
git diff --cached
git commit -m "feat(frontend): improve task catalog and filters"
git push -u origin feat/frontend-catalog
```

Команда `git add frontend` добавляет все изменения этой папки. Если там есть посторонняя работа, перечислите конкретные изменённые файлы вместо целой папки. Для backend и AI используйте свои пути и свою ветку. `git diff` не показывает содержимое новых неотслеживаемых файлов; после `git add` проверяйте их через `git diff --cached`.

После первого push с `-u` повторная отправка в **той же ветке** выглядит так:

```powershell
git add frontend
git diff --cached
git commit -m "fix(frontend): handle empty catalog"
git push
```

Для backend пример: `git add backend/app/services/submissions.py`. Для AI: `git add backend/app/services/ai backend/app/routers/ai.py`. Добавляйте также свои изменённые тесты и документацию; не копируйте примеры путей без проверки `git status`.

Делайте небольшой законченный commit после одной исправленной ошибки или функции. Ветку можно пушить незавершённой и открыть Draft PR; объединять её нужно после проверки.

## 6. Как объединять работу

1. Откройте репозиторий GitHub → `Pull requests` → `New pull request`.
2. `base` — основная ветка (`main`), `compare` — ваша ветка.
3. В описании напишите: что изменено, как проверить, менялись ли API/миграции/переменные окружения.
4. Другой участник смотрит diff и результаты проверки. Для изменений frontend ревью делает участник 2 или 3; для backend — 3; для AI и инфраструктуры участника 3 — 2.
5. Участник 3 координирует объединение через доступную кнопку `Merge pull request` или `Squash and merge`. Свой PR объединяет только после проверки другим участником.
6. Изменения после ревью пушьте в ту же ветку: они попадут в тот же PR.
7. После объединения все обновляют `main` через `git switch main` и `git pull --ff-only origin main`. Следующая задача — новая ветка от обновлённой `main`.

Не нужно ждать готовности всех трёх больших частей. Объединяйте небольшие совместимые изменения по мере готовности. Если меняется API, сначала согласуйте контракт, затем объединяйте сервер, AI и использующий их интерфейс в согласованном порядке, сохраняя работоспособность общей версии.

## 7. Как забрать изменения коллег в свою рабочую ветку

Если ваш PR ещё не объединён, а в `main` появились изменения коллег, сначала закоммитьте свою текущую работу. Находясь в своей ветке, выполните:

```powershell
git fetch origin
git merge origin/main --no-edit
```

После успешного объединения повторите проверки и выполните `git push`. Merge позволяет обновить ветку без переписывания истории и без `push --force`.

### Если возник конфликт

1. `git status` покажет конфликтующие файлы.
2. Откройте их в редакторе. Согласуйте итог с владельцем файла; не выбирайте автоматически «всё моё» или «всё входящее».
3. Уберите маркеры `<<<<<<<`, `=======`, `>>>>>>>`, сохранив нужные изменения обеих сторон.
4. Добавьте исправленные файлы и завершите merge:

```powershell
git add путь/к/исправленному/файлу
git commit -m "merge: resolve changes from main"
```

5. Запустите проверки, затем `git push`.

Если решили отменить ещё не завершённый merge, используйте `git merge --abort`. Команда предполагает, что до merge рабочая папка была чистой, как описано выше.

Если push отклонён как `non-fast-forward`, кто-то изменил **вашу удалённую ветку**. Проверьте с командой, затем из своей ветки: `git fetch origin`, `git merge origin/ИМЯ-ВАШЕЙ-ВЕТКИ --no-edit`, проверки, `git push`. Не применяйте force push.

Если отклонён `git pull --ff-only` на `main`, остановитесь: в локальной `main` есть своя расходящаяся история. Сначала сохраните её отдельной веткой и разберите ситуацию с ответственным за сборку; не используйте `reset --hard` для быстрого обхода.

## 8. Проверки перед объединением

Установка и запуск описаны в README. При локальной работе используйте своё Python-окружение `.venv` в корне проекта и `pnpm` для frontend. После изменения зависимостей обновите окружение; после изменения БД примените миграции.

Backend, из корня проекта в PowerShell, после установки зависимостей:

```powershell
cd backend
..\.venv\Scripts\python.exe -m pytest -q
cd ..
```

Frontend:

```powershell
cd frontend
pnpm install --frozen-lockfile
pnpm build
cd ..
```

Если меняете frontend-зависимости, используйте `pnpm add ...` / `pnpm add -D ...` и коммитьте вместе `package.json` и `pnpm-lock.yaml`. Команда с `--frozen-lockfile` намеренно завершается ошибкой при рассогласовании. Не добавляйте второй lockfile от npm в общую работу.

В ограниченной Windows-среде portable-сборка описана в README. Она не заменяет проверку стандартной сборки на целевой среде.

Финальная проверка участника 3: чистый clone, установка по README, миграция, seed и повторный seed, запуск, затем весь сценарий: компания → задача → студент → проект → анонимное рассмотрение → завершение приёма → победитель → оценка 95 → по 31.67 трём участникам → модерация. Для Docker следуйте README; сам факт наличия Dockerfile не означает, что контейнерный запуск проверен.

## 9. Что не должно попадать в GitHub

- API-ключи и токены, в том числе внутри исходников, команд в README, скриншотов и логов.
- `.env`, `.env.local`, другие `.env.*` с настройками; разрешён только шаблон `.env.example` без настоящих секретов.
- `.venv`, `node_modules`, базы `*.db` / `*.sqlite` / `*.sqlite3`, кэши и `dist`.

Эти env-файлы, зависимости и базы исключены в `.gitignore`. Он не защищает секрет, вставленный в обычный `.py`/`.ts`, и не удаляет файлы, которые уже были закоммичены. Если ключ попал в GitHub, сразу отзовите его у провайдера; удаления строки новым коммитом недостаточно.

У каждого свой локальный `.env`. В репозитории передавайте только имена переменных и пустые/демонстрационные значения через `.env.example`.

Это предлагаемый график команды, а не расписание организаторов. Ориентируйтесь на фактический дедлайн платформы. Последние 30–40 минут оставьте для исправлений и сдачи.

## 11. Последняя отправка

На GitHub проверьте, что финальные PR объединены именно в основную ветку. В чистой локальной `main`:

```powershell
git pull --ff-only origin main
git status
git log -1 --oneline
```

Запишите hash итогового коммита в описание сдачи при необходимости. Незакоммиченные файлы на ноутбуке и изменения только в отдельной ветке в финальную версию не входят.

На платформе: страница треков → ваш кейс → «Сдать решение» → название и описание → подтверждение отправки. Добавляйте ссылку на развёрнутую версию только если она действительно существует и доступна жюри: `localhost` работает только на вашем компьютере.

## Справка
